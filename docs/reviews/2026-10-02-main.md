## Major
### 🟠 Unreachable follow up flag with two short truths, `src/lib/rules/engine.ts:686`
**Problem**: You keep `isFollowUp` on `renderAlert`, but `runRulesEngine` never passes it as true, and the worker uses `renderWhatsAppFollowUp` for shorts instead. The two paths build different action blocks for `HIGH_RISK` with a special category, one from `nextStep` and one from fixed generic copy.
**Why it matters**: You invite a future caller to pass the flag and expect the tested short, while production sends the other short, so phishing or pressure guidance can go missing in a short note where safety matters most.
**Suggested fix**: You should pick one short builder and remove the other path, then lock the kept path with a test for each verdict that asserts the action block you intend.

### 🟠 Marker write rides after send outside the decision write, `src/inngest/functions/process-whatsapp-message.ts:289`
**Problem**: You record the decision, then you send, then you write the tone marker in a separate call, while the governing spec asks for the marker to ride with the decision record write under the per sender order.
**Why it matters**: You can send twice when the marker call fails after a send and the step reruns, since the rerun counts again and sends again, which costs you a billed message and confuses the person with a duplicate.
**Suggested fix**: You should make the post send writes atomic with the decision write where you can, or make the retry safe by checking the stored marker before you count and send again.

## Minor
### 🟡 Tone gate reads before window open with separate clock, `src/inngest/functions/process-whatsapp-message.ts:88`
**Problem**: You read the thread row in `check-tone-gate` before you call `openThread`, and you use `Date.now` for liveness while the window uses inbound time from `windowStart`. You also pay for a second read that `openThread` repeats.
**Why it matters**: You can turn a live window thanks into a full when the worker runs late, since `Date.now` sees expiry while inbound time still sees live, which costs you an extra model call, and you keep two sources of truth for one marker.
**Suggested fix**: You should reuse the marker that `openThread` returns and drop the early read, so window and tone share one clock and one row.

### 🟡 Opened window tone fields go unused by the worker, `src/lib/whatsapp/thread.ts:109`

**Why it matters**: You risk a future truthy check passing on an invalid date, which could mark a thread as already answered when it has no valid full.
