# 0002. Auth refresh (password plus Google plus user button)

**Date**: 2026-09-25

## Summary

One permit gate covers sign up, sign in, Google, verify, reset, and sign out, and the happy path lands in chat with the avatar menu live. Password users verify mail before real chat, Google arrivals skip verify since Google already proved the mail, and sessions last weeks with revoke on password change. Zero schema migration, the four Better Auth tables are reused as they are.

## Requirements

**User stories**:
- As a new visitor, I want one gate for sign up plus sign in so that I stop guessing which page does what.
- As a Google user, I want one tap entry so that I reach chat without a password.
- As a password user, I want verify plus reset that actually arrive so that I never lose my account.
- As a signed in user, I want an avatar menu with settings plus sign out so that my account stays in reach.

**Acceptance criteria**:
- **AC-1**: a new password user signs up, verifies by mail, and lands in chat with the avatar menu live.
- **AC-2**: a Google user joins in one tap with `emailVerified` set true at create as the already proved flag, always as a fresh user plus a google `Account` row; a Google mail matching a password account fails closed with a sign in with password note.
- **AC-3**: an unverified password user who tries to chat is blocked by a resend verify panel, not a dead end.
- **AC-4**: an expired verify (24h) or reset (1h) link shows expired plus one tap to request a fresh link.
- **AC-5**: reset works through an expiring mail link (1h, reusable within its window), and an OTP code path ships in the same child (10 min code from the mail OTP plugin, delivered by the `0003-mail` job).
- **AC-6**: passwords need 8 plus chars with a weak, fair, strong hint, sessions last 30 days, password change revokes all sessions.
- **AC-7**: resend verify is capped at 5 per hour per mail plus 20 per day per IP, OTP check at 10 per hour per mail, all behind Arcjet.
- **AC-8**: cancelled or failed Google returns to the gate with the mail form kept plus a retry note.
- **AC-9**: a lost session cookie sends the user to the gate with guest tries intact (counter owned by the `0004-chat-memory` API).
- **AC-10**: errors are field level bilingual messages from `src/lib/i18n/dictionary.ts` keys plus machine codes, with `sonner` toasts for action outcomes.
- **AC-11**: roles stay untouched and `requireModerator` keeps gating admin.
- **AC-12**: a failed or slow mail job shows an honest delayed state with retry, fed by the `0003-mail` job status endpoint, never fake success.
- **AC-13**: password sign up takes optional name, avatar falls back to initials when name and image are empty.

## Options considered

### Option 1: Better Auth built ins plus two customs

Keep Better Auth for sign up, sign in, Google, sessions, and tokens, and add only a resend verify action plus an OTP check action. Mail flows ride the `0003-mail` jobs.

**Pros**:
- Least new code on the attack face, the library owns hashing, tokens, and OAuth.
- Zero schema change, the four tables already fit.

**Cons**:
- Bound to Better Auth behavior for edge cases like OAuth linking.

### Option 2: Custom endpoints for everything

Hand rolled password check, OAuth exchange, token tables, and session cookies.

**Pros**:
- Full control over every rule and message.

**Cons**:
- Rebuilds solved problems like token rotation and session fixation, each a breach risk.

### Option 3: Separate pages per action

Distinct routes for sign up, sign in, verify, and reset instead of one gate.

**Pros**:
- Deep linkable steps with clear browser history.

**Cons**:
- Scatters one job across pages the user must learn.

## Decision

**Chosen option**: Option 1: Better Auth built ins plus two customs

One gate screen backed by Better Auth plus a resend verify action plus an OTP check action, with Google provider, mail OTP plugin, 30 day sessions with revoke, and 8 plus hint password policy.

## Rationale

The gate is the attack face, so boring and proven wins over control. Context forces are a live Better Auth base with zero auth UI, a mail child that owns sending, and GA rigor on trust flows. Option 1 keeps the new code tiny and reviewable while meeting every accepted answer. The engineer picked always fresh Google users over mail linking, so duplicate accounts across methods stay possible and are recorded as follow-up rather than silently merged.

## Feature design

**Data model sketch**:
No new tables and no new columns. `User` (id, email unique, `emailVerified`, name, image, role), `Session` (token unique, `userId` FK, `expiresAt` 30 days), `Account` (provider plus account id per login method, `userId` FK), `Verification` (identifier, value, `expiresAt`, single use). Google arrivals always create a fresh `User` with `emailVerified` true plus a google `Account` row. The mail state flag on the user row is exactly `emailVerified`, so the umbrella contract holds with zero migration. Password sign up name is optional and the avatar falls back to initials.

**State transitions**:
anonymous to verify pending to verified to signed in. Signed in to signed out on demand, on cookie loss, or on password change revoke all. Verify and reset values are single use and die on expiry or first use.

**API surface**:
| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `/api/auth/*` | mixed | per Better Auth action | session, user | public plus session | 400, 401, 403, 429 |
| resend verify action | POST | email | queued job id | public, capped 5/hr per mail plus 20/day per IP | 400, 429 |
| OTP check action | POST | email, code single use 10 min | session | public, capped 10/hr per mail | 400, 401, 410 |

**Value sourcing**:
| Action | Value produced / displayed | Source |
|---|---|---|
| gate helper | may chat yes or no | derived from session plus `User.emailVerified` plus Google pre proved flag |
| resend action | queued job id | returned by the `0003-mail` job sender |
| resend panel | tries and caps copy | caps from this spec, counts from the sender |
| OTP check | session | Better Auth mail OTP plugin consuming a `Verification` row |
| OTP code value | 10 min code shown to user | generated by the mail OTP plugin, delivered by the `0003-mail` job |
| user button | avatar plus name | `User.image` plus `User.name`, Google fills both, password fallback is initials |
| gate copy | bilingual strings | `src/lib/i18n/dictionary.ts` keys, new gate keys added with the build, nothing invented |
| reset request | honest delayed state | Inngest job status from the `0003-mail` status endpoint, gate polls with retry copy |
| guest wall | tries left today | browser id plus IP hash counter owned by the `0004-chat-memory` API |

**Key invariants**:
- Password users with `emailVerified` false never reach real chat beyond guest tries.
- Verify links live 24h and reset links 1h as stateless signed tokens, reusable within their window; OTP codes live 10 min and are single use.
- Sessions live 30 days and every session dies on password change.
- Passwords need 8 plus chars with a weak, fair, strong hint from length plus variety plus a common password blocklist.
- Resend and OTP check stay capped per mail plus per IP behind Arcjet.
- A Google mail matching a password account fails closed with a sign in with password note, never a silent duplicate.

**Security model**:
Self only account edits, admin only role assignment, `requireModerator` unchanged. Auth failures log without PII. Rate plus bot cover on gate, resend, reset, and OTP check. Weeks long sessions are server side expirable and revocable.

**Configuration required**:
- `GOOGLE_CLIENT_ID`: Google Cloud OAuth web client id
- `GOOGLE_CLIENT_SECRET`: Google Cloud OAuth web client secret
- `BETTER_AUTH_SECRET`: already present, signing stays
- Mail keys (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM`) are owned by `0003-mail`

**Critical test scenarios**:
- Happy path: sign up to verify to chat with avatar live, verifies **AC-1**
- Failure case: expired link shows expired plus reissue, verifies **AC-4**
- Auth/permission: unverified chat attempt blocked with resend, verifies **AC-3**

## Migration plan

**Strategy**: no migration needed
**Phases**:
1. Ship config plus gate plus customs behind current routes, old password flow keeps working since storage is unchanged.
**Rollback**: revert the commit, sessions and users are untouched.
**Risks**: Google project misconfiguration fails closed at the provider step, surfaced by **AC-8** copy.

## Build plan

Journey order, gate first then states then guards:

1. Wire Google provider plus env plus callback, satisfies **AC-2**, **AC-8**
2. Build one gate screen (masthead plus Google plus mail form plus verify plus reset states, owned shadcn set, type plus stamp only, i18n keys, initials fallback), satisfies **AC-1**, **AC-2**, **AC-8**, **AC-10**, **AC-13**
3. Enforce verify before chat with block plus resend panel, satisfies **AC-3**
4. Add reset link plus OTP code paths with expiry plus reissue, satisfies **AC-4**, **AC-5**
5. Tune sessions to weeks, revoke on password change, cap resend plus OTP behind Arcjet, satisfies **AC-6**, **AC-7**
6. Add gate helper plus honest mail states plus cookie loss path, satisfies **AC-9**, **AC-12**, **AC-11**

## Consequences

**Positive**:
- One trusted gate replaces scattered auth states.
- Zero migration risk, existing users keep sessions.

**Negative / tradeoffs**:
- Always fresh Google users can duplicate accounts when one human uses both methods.
- Weeks long sessions raise takeover window, contained by revoke on password change.

**Neutral**:
- Design source is a connected design tool, file plus frames still owed before build.
