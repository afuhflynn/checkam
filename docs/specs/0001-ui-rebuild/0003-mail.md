# 0003. Mail plumbing (Nodemailer plus Inngest)

**Date**: 2026-09-25

## Summary

Three Inngest jobs share one pooled Nodemailer transport to send verify, reset, and welcome mails as rich bilingual HTML with plaintext twins. Payloads stay small with event id dedupe, status lives in Inngest run history behind a gate status endpoint, and failures stay visible with retry plus an ops alert. No new tables.

## Requirements

**User stories**:
- As a new password user, I want verify mail that arrives fast so that I reach chat the same sitting.
- As a locked out user, I want reset mail with link plus code so that I recover even when links break.
- As a fresh verified user, I want one short welcome so that I know what to check first.
- As the gate, I want honest job status so that I never fake success.

**Acceptance criteria**:
- **AC-1**: sign up queues a verify job that delivers a link (24h) in the user locale, link built as `NEXT_PUBLIC_APP_URL` plus `/verify?token=` plus value.
- **AC-2**: reset request delivers link (1h, `NEXT_PUBLIC_APP_URL` plus `/reset?token=` plus value) plus OTP code (10 min) in one mail, code generated by the `0002-auth` plugin path before the job and passed by verification id only.
- **AC-3**: welcome sends once after verify completes, never for Google arrivals, triggered from the Better Auth verify callback and skipped when any `Account` row has provider google.
- **AC-4**: every mail is rich bilingual HTML with a plaintext twin, copy from i18n keys, one link or code each, locale from the request payload with `Accept-Language` fallback and no stored column.
- **AC-5**: sends retry 3 times at 1, 5, 15 min backoff, then stay failed while the gate shows delayed with retry through the status endpoint; `retrying` maps to `delayed`.
- **AC-6**: public triggers stay capped at 5 per hour per mail plus 20 per day per IP for reset and resend, 10 per hour per mail for OTP adjacent checks, all behind Arcjet; system triggers stay internal only with no public route.
- **AC-7**: a duplicate event never sends twice, the event id `mail:{type}:{userId}:{verificationId}` is the idempotency key; resend while a verify job is still queued returns the existing job id instead of a new event.
- **AC-8**: SMTP down past retries stays failed and visible with an ops alert firing to `ALERT_WEBHOOK_URL`.
- **AC-9**: empty SMTP config fails loud at boot in dev, never silently; the trigger returns the job id to the client and the gate polls status by it.

## Options considered

### Option 1: Three jobs plus one pooled sender

Verify, reset, and welcome as separate Inngest functions sharing one tuned SMTP transport and one template layout.

**Pros**:
- Each mail has its own retry and history, one sender keeps behavior consistent.
- Small payloads keep PII out of event logs.

**Cons**:
- Three functions to own instead of one.

### Option 2: One generic send job

A single function with a type field rendering any mail.

**Pros**:
- Less scaffolding, one place to watch.

**Cons**:
- Retry, caps, and history blur across mail kinds with different urgency.

### Option 3: Status in a new log table

A mail log table backing the status endpoint.

**Pros**:
- Queryable history in your own DB.

**Cons**:
- New table for data Inngest already keeps, against the history only pick.

## Decision

**Chosen option**: Option 1: Three jobs plus one pooled sender

Nodemailer pooled transport from env, `react-email` component templates with plaintext twins, small idempotent payloads, Inngest run history as the status source, caps plus internal triggers, visible failure with alert.

## Rationale

Mail kinds differ in urgency and trigger, so separate jobs earn their keep while one sender keeps them coherent. History only avoids a table for state the runner already stores, and the gate endpoint reads it instead. Rich bilingual HTML honors the bilingual country pick, with a component library over literals because the engineer chose library rendering. `react-email` is the call since it renders static HTML without a browser, with template literals as runner up if the dep proves heavy.

## Feature design

**Data model sketch**:
No new tables and no new columns. Job payload is recipient id plus mail type plus token reference plus locale. `emailVerified` on `User` remains the mail state flag per the umbrella contract. OTP code values live in `Verification` per `0002-auth`.

**State transitions**:
queued to sending to sent, or queued to sending to retrying to failed. Failed stays terminal and visible until a fresh trigger starts a new job. Welcome fires once on the verify completed transition, never twice.

**API surface**:
| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| verify trigger | internal `inngest.send`, no public route | user id, locale | job id | system only | 500 |
| reset trigger | POST | email, locale | job id | public, capped 5/hr per mail plus 20/day per IP | 400, 429 |
| resend trigger | POST | email, locale | job id, existing id when still queued | public, capped 5/hr per mail plus 20/day per IP | 400, 429 |
| welcome trigger | internal on verify callback | user id | job id | system only | 500 |
| job status endpoint | GET | job id | queued, sending, retrying mapped to delayed, sent, failed plus timestamps | session owner only | 404, 429 |

**Value sourcing**:
| Action | Value produced / displayed | Source |
|---|---|---|
| verify job | 24h link | `0002-auth` token path stored as `Verification` row, link builder owns shape |
| reset job | 1h link plus 10 min code | `0002-auth` plugin values created before the job, job receives verification id only and reads the row, codes never ride events |
| welcome job | first check suggestions | static template copy from i18n keys, fired from the verify callback |
| mail body | rich HTML plus plaintext | `react-email` components plus generated twin |
| gate poll | queued, sent, failed | status endpoint reading Inngest run history by job id |
| dedupe | single send per event | event id as idempotency key |

**Key invariants**:
- One event id `mail:{type}:{userId}:{verificationId}` never produces two sends.
- Public triggers stay capped per mail plus per IP behind Arcjet.
- The pooled transport runs max 5 connections with a 10s timeout.
- Boot with empty SMTP config fails loud in dev.
- Failed stays failed and visible, retry starts a new job, never rewrites history.
- Welcome fires exactly once per user and never for Google arrivals.

**Security model**:
System triggers accept internal calls only. Public triggers validate with Zod plus caps. Payloads carry ids and references, never passwords or codes at rest beyond the `Verification` rows `0002-auth` owns. Logs hash recipient mail.

**Configuration required**:
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`: pooled transport (timeouts plus pool tuned)
- `EMAIL_FROM`: sender identity `CheckAm <no-reply@checkam.cm>`
- `ALERT_WEBHOOK_URL`: ops alert target for SMTP down past retries, empty means log only in dev
- Alert target for SMTP down past retries (ops channel, named at build)

**Critical test scenarios**:
- Happy path: sign up to verify mail delivered in locale, verifies **AC-1**
- Failure case: SMTP down through retries stays failed with alert plus gate retry, verifies **AC-5**, **AC-8**
- Auth/permission: uncapped resend flood is capped, verifies **AC-6**

## Migration plan

**Strategy**: no migration needed
**Phases**:
1. Ship transport plus templates plus jobs plus triggers plus status endpoint, old auth keeps working throughout since no sender existed before.
**Rollback**: revert the commit and disable triggers, queued jobs drain.
**Risks**: sender reputation on a fresh domain lands mails in spam, contained by plaintext twins plus short copy plus gradual volume.

## Build plan

1. Build pooled transport plus env plus health check, satisfies **AC-5**, **AC-8**
2. Build shared layout plus three bilingual templates with twins, satisfies **AC-4**
3. Build three jobs with small idempotent payloads plus retries, satisfies **AC-1**, **AC-2**, **AC-3**, **AC-7**
4. Wire triggers with caps plus internal guards, satisfies **AC-6**
5. Build status endpoint plus gate poll plus delayed copy plus alert plus boot check, satisfies **AC-5**, **AC-8**, **AC-9**

## Consequences

**Positive**:
- Auth owns its promised sending with honest states.
- History only means zero schema to maintain.

**Negative / tradeoffs**:
- Status reads depend on Inngest run history availability in every env.
- Rich HTML costs template upkeep across two languages.

**Neutral**:
- `react-email` is a new dep to install and record.

## Amendments (peer review pass, 2026-09-25)

- Status stays domain derived (verified means sent, fresh token means sending) instead of Inngest history read; the gate needs no Inngest API key. History read remains follow-up.
- Link and code reset flows are separate triggers sharing one template; each mail carries what its flow provided.
- Welcome exactly once relies on the pair-unique marker with catch on race.
- Retries run in-function at 1, 5, 15 minutes with a single alert path; `retries: 0` on the function itself.
- Accepted deviations: OTP per-mail hourly cap (see 0002); resend markers double as the cap ledger.
