# 0011. Share message rewrite - rationale

## Context

The share message is generated by `renderAlert` in `src/lib/rules/engine.ts`. It produces two versions: a markdown version for WhatsApp (which renders `*bold*`) and a plain text version for Facebook and SMS (which do not). The message is built from the verdict, evidence bullets, phone numbers, and a safety note.

The current share message has a problem: it looks like AI generated content. It uses all caps headers, too many emojis, and a structure that feels machine generated rather than human written. When someone receives this message, it is immediately obvious it came from a bot, which undermines the trust the verdict is trying to build.

The share message is the most user facing artifact in the product. It is what gets forwarded to family and groups. It needs to read like a concerned friend who checked something, not like a security system firing an alarm.

## Options considered

### Option 1: Fix in place

Rewrite the `renderAlert` function in `engine.ts` to produce the new format. The function signature and return shape stay the same. Only the internal rendering logic changes.

**Pros**:
- No new files, no new dependencies, no API changes.
- The change is contained to one function.
- Easy to review and revert.

**Cons**:
- The function grows more complex as it handles more conditional sections.
- Testing requires covering all verdict and evidence combinations.

### Option 2: Replace with a dedicated share message builder

Create a new `share-message.ts` module that takes a `VerificationResult` and produces the share text. The `renderAlert` function delegates to this new module.

**Pros**:
- Separates share message rendering from the rules engine.
- Easier to test in isolation.
- Clearer ownership of the share message format.

**Cons**:
- Adds a new file for a single function's worth of logic.
- The rules engine already owns the verdict data; splitting the rendering creates a seam that may not need to exist.

### Option 3: Replace with a template approach

Use a template string with placeholders for each section. The template is filled in based on the verdict and evidence.

**Pros**:
- Very easy to read and modify.
- The structure is visible at a glance.

**Cons**:
- Templates become unwieldy with this many conditional sections.
- Harder to test individual sections.
- String interpolation gets messy with the markdown vs plain text distinction.

## Rationale

The share message rendering is a presentation concern that belongs with the verdict engine that produces the data. The `renderAlert` function already has access to everything it needs: the verdict, the evidence bullets, the phone numbers, the entity, and the safety note. Creating a separate module would add a seam without adding clarity.

The fix in place approach keeps the change contained and reviewable. The function is already the single source of truth for share message rendering. Rewriting it in place means there is one place to look for share message format, not two.

The template approach was considered and rejected because the number of conditional sections (phone, email, entity, amount, payment method, safety note, hotline, forward prompt) would make a template string unreadable. The current function already uses conditional logic to build the message; the rewrite makes that logic cleaner, not more complex.
